# 짧은 요청에서 Plan과 Task까지

고객의 짧은 요청을 프로젝트·코드 조사, 핵심 합의, 실행 가능한 계획으로 발전시킨다. 요청자에게 계획 양식을 작성하도록 요구하지 않는다. 확정된 Issue와 작은 명확한 수정은 필요한 부분만 사용하며 재발행하지 않는다.

## 요청과 프로젝트 조사

고객 원문과 에이전트의 해석을 구분하고 대상 사용자·문제 상황·기대 변화를 정리한다. 현재 저장소의 지침, README, 도메인 문서, ADR, 기존 Issue부터 읽는다. 기존 Notion Project·Repository 관계와 프로젝트 안내를 통해 관련 저장소로 탐색을 넓힌다.

프로젝트 안내에는 목적·담당 영역, 저장소·핵심 문서 링크, 연결 프로젝트·주요 계약, 결정 담당자와 확인 출처를 사용한다. 안내가 없으면 이번 Plan에 관련 프로젝트만 요약한다. 없는 정보를 추측하거나 새 DB를 자동 생성하지 않는다. 접근하지 못한 자료는 확인 한계로 남긴다.

블루프린트는 팀이 합의한 목적·도메인 경계·계약·제약이다. 현재 구현과 향후 구상을 구분하고 이번 요청으로 달라질 부분을 표시한다. 기존 블루프린트가 없으면 코드에서 확인한 현재 구조를 초안으로 남긴다.

## Graft 코드 조사

같은 설치본의 `skills/ultivis-flow/references/graft-code-map.md`를 읽고 CLI·캐시 정책을 따른다. 설정 저장소의 원본은 `codex/skills/ultivis-flow/references/graft-code-map.md`다.

- 관련 저장소별로 `graft map`, `graft ask`, `graft skeleton`, `graft callers`를 목적에 맞게 사용해 진입점·처리 흐름·재사용 구현·변경 영향·관련 테스트를 찾는다.
- 중요한 판단은 원본 코드·문서와 대조하고 필요하면 테스트나 작은 실험으로 확인한다. 참조 관계만으로 런타임 동작을 확정하지 않는다.
- Graft 누락·오류·지원하지 않는 영역은 `rg`와 직접 읽기로 조사하고 한계를 남긴다. 설치 문제 때문에 기획을 중단하지 않는다. 그래프는 worktree별로 유지한다.
- 저장소 간 API·이벤트·패키지 관계는 생산자와 소비자 양쪽 계약을 확인한다. 모든 프로젝트를 일괄 탐색하지 않는다.

조사 완료 기준: 현재 동작·재사용할 부분·변경 경계·검증 방법에 근거가 연결되고, 사실·가정·팀의 미결 결정이 구분되어 있다.

## 해석과 핵심 합의

사용자에게 먼저 짧게 제시한다: **이렇게 이해했습니다 / 확인한 현재 상태 / 추천 해결 범위 / 남은 결정**. 조사 로그 전체를 승인 자료로 넘기지 않는다.

코드에서 알 수 있는 사실은 조사한다. 사용자 업무·우선순위·제품 동작처럼 조사로 정할 수 없는 중요한 결정에 `grilling`을 사용한다. 일반 요청에서는 중요한 미결 결정에 집중해 한 번에 한 질문씩 추천안·이유·대안의 영향을 설명한다. 명시적인 심층 grilling은 기존 인터뷰 방식을 유지한다.

정상·실패·경계 사례로 같은 동작을 이해하는지 확인한다. 해결안에는 선택 이유, 중요한 대안과 단점, 포함·제외 범위, 유지할 계약과 블루프린트 변화를 담는다. 방안을 좌우하는 가정은 검증 질문·실험·종료 조건이 있는 조사 작업으로 먼저 확인하고, 결과에 의존하는 후속 작업은 초안으로 둔다.

합의 완료 기준: 성공 사례·결정과 이유·제외 범위·미결 사항을 팀이 확인할 수 있다. 이미 받은 승인은 반복 요청하지 않으며 추천안에 대한 동의를 새로운 범위의 승인으로 확대하지 않는다.

## Plan과 Task 분해

작업 규모에 맞춰 다음을 담는다. 짧고 명확한 작업은 한 문단으로 충족해도 된다.

| Story / Plan | Task별 내용 |
|---|---|
| 요청 원문, 문제와 대상 사용자 | 결과와 연결된 성공 사례 |
| 정상·예외 동작과 성공 조건 | 포함·제외 범위와 Repository |
| 포함·제외 범위, 유지 조건 | 선행 결정·Task·소비할 산출물 |
| 방안, 선택 이유, 블루프린트 변화 | 테스트·데모·완료 확인 방법 |
| 근거 링크, 가정·미결 결정 | 관련 코드·계약 근거 |
| 재합의 경계, 최종 확인 역할 | 확정 또는 실험 결과 대기 여부 |

- `의도 → 성공 사례 → 해결안 → Task → 검증 증거`를 연결한다. 담당 Task가 없는 성공 사례와 목적에 연결되지 않는 Task를 발행 전에 정리한다.
- Task는 독립적으로 검토할 작은 결과로 나눈다. 에이전트 수·파일 수·DB/API/UI 계층만으로 분해하지 않는다. 내부 구현 단계는 체크리스트로 둔다.
- 여러 저장소나 공통 기반 때문에 나누면 생산자·소비자의 API·이벤트·스키마·버전과 검증 방법을 명시한다. Task 하나는 Repository 하나를 갖는다.
- `Parent Task`는 선행 의존성이다. 같은 파일·계약의 동시 변경 가능성도 확인한다. Ready 판정은 병렬 에이전트 실행 권한을 부여하지 않는다.
- 바로 실행할 작업부터 구체화한다. 불확실한 후속 작업에 임의의 일정·확정 구현안을 부여하지 않는다.

## 발행과 변경, 결과 확인

현재 대화에서 확정한 Plan을 기존 `tmp/current-plan.md` 관례에 맞춰 보존한다. Plan과 Task 구성이 확인되면 기존 발행 명령에 맡긴다. 요청과 Story는 항상 1:1이 아니다. 기존 active Story를 활용할 때도 Project 경계와 의도를 확인한다.

Story `body_markdown`에는 의도·범위·선택·근거·성공 사례를, Task `description`에는 결과·범위·의존성·검증을 전달한다. 새 스키마 필드를 가정하지 않는다. 새 Task 간 의존성은 Plan에 이름으로 적되 `parent_task_ids`에는 실제 Notion ID만 사용한다. ID가 없는 후속 Task는 선행 Task 생성 후 기존 Task 추가 흐름에서 발행한다.

합의 범위 안의 구현 순서·내부 설계·테스트 수정은 진행하고 중요한 변경 이유를 기록한다. 범위·성공 조건·외부 계약·중요 비용이 달라지거나 핵심 가정이 무너지면 영향과 대안을 제시하고 해당 결정에 의존하는 작업을 재합의한다.

결과는 사례별 증거, 남은 제한·미검증 사항, 실제 블루프린트 변화로 보고한다. PR 병합·기술 검증과 사용자 결과 확인을 구분한다. 배포가 성공 조건이면 별도 확인하며 기존 상태 스키마를 임의로 변경하지 않는다.

## 적용 예와 평가

“장비가 끊기면 알려주세요”를 받으면 상태 판정·알림·권한을 조사한 뒤 허용 단절 시간처럼 고객 업무에 관한 미결 결정만 묻는다. 기존 알림 재사용 여부를 확인하기 전에 알림 시스템 신설 Task를 발행하지 않는다.

짧은 신규 요청, 확정된 Issue, Graft 누락, 여러 저장소의 계약 변경, 핵심 가정 불성립 사례로 방법을 평가한다. 불필요한 질문·중복 발행 없이 근거 있는 방안과 검증 가능한 Task에 도달하는지 확인한다. 문서·배포본 검사는 실제 팀의 이해도나 계획 품질을 증명하지 않는다.
